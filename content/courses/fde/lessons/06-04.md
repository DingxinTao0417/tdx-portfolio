# 异步任务、定时执行与渠道

## 学完能做什么

你能区分请求受理与任务完成，设计异步状态、重复触发处理和通知边界。

## 核心概念

异步任务是先受理请求，再在后台执行。定时任务增加了触发时间和频率；渠道决定结果送到哪里。三者都要明确身份、任务范围、时区、停止条件和通知许可，不能只写“稍后处理”。

任务通常需要任务 ID、幂等键、状态查询、超时处理和取消规则。写操作超时只说明没有及时取得结果，不证明写入失败。应先查询可靠状态；盲目重试可能创建重复工单。

## 情境拆解

虚构企业想每天查看模拟维修工单。纸面设计应写明使用哪个时区、检查什么、由谁接收，以及没有变化时是否保持安静。本练习不启用真实定时服务，也不向真实群聊发送通知。

模拟创建请求超时后，助手先报告“结果待确认”，用任务 ID 或幂等键查询。确认已创建才报告成功；确认未创建且规则允许时再重试。

## 常见误区

“已受理”不是“已完成”；换一个通知渠道也不产生发送权限。取消任务可能只阻止后续步骤，无法撤销已发生的写入，需要另外核实。本课必修是状态设计，定时执行与渠道集成为演示或选修实现。

## 接受任务不等于完成任务

本课是选修扩展。异步处理需要区分排队、运行、成功、失败、未知和取消。用户看到“已接受”，只能说明任务进入了队列。

取消请求也可能发生在写入之后。停止后续步骤不等于撤销已经产生的业务记录，最终状态仍需核对。

## 动手：写异步任务状态表

1. 设定一个模拟批量资料处理任务，列出触发条件、时区、任务标识和输入版本。
2. 写明各状态如何转换，何时允许重试，何时必须先查询原任务。
3. 设计取消、超时和重复触发三个例子，核对已经产生的结果。
4. 如需通知，只设计获准接收者和最小内容。本课不实际启用调度、邮件或付费资源。

~~~text
任务标识 / 触发 / 时区：
输入与允许范围：
当前状态及来源：
下一步转换：
重复触发与去重：
取消能停止什么 / 不能撤销什么：
通知接收范围：
最终结果与未知项：
~~~

### 检查产物

排队、运行和完成没有混用。取消后有明确的状态说明；通知不发送越权资料。模块案例中可以保持简单同步流程，不必为完成选修而强加异步架构。
