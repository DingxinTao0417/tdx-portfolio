前沿部署工程师（Forward Deployed Engineer，FDE）需要把用户的业务问题转成可实现的软件方案。[Palantir 的官方岗位说明](https://jobs.lever.co/palantir/c4442730-2926-41ad-8c0e-5e5a6b4d14ae)将直接理解客户问题、设计和实现解决方案列为这一角色的职责。

下面从需求澄清、系统集成和评测整理对这一角色的理解，重点是每一步要留下什么可检查的结果。

## 从需求到可验证的交付

以文档问答系统为例，功能说明、权限规则和验收样例需要相互对应。只看演示中的回答，很难判断系统是否适合实际工作流程。

### 1. 澄清需求和验收标准

需求讨论可以从具体使用场景开始：

- 用户希望得到什么结果，能否提供一个合格答案的例子？
- 哪些资料可以作为依据，不同身份分别能访问什么？
- 现有流程在哪里受阻，系统无法处理时由谁接手？

把确认后的问题、参考答案和适用条件整理成评测样例，再写清楚验收方式。样例需要覆盖资料缺失、权限不足等情况，才能检查系统是否会在这些场景下给出不恰当的回答。

### 2. 按现有系统的规则完成集成

接入身份认证、文档库或工单接口时，需要先确认数据格式、调用权限和错误处理方式。下面的检索代码是权限过滤的示意，辅助函数由具体系统实现；其中的参数只是示例配置。

```ts title="acl-filter.ts"
// 每一次检索调用都以调用者的有效权限为范围。
// 无法解析权限时，默认拒绝——绝不默认放行。
export async function retrieve(query: string, user: User) {
  const acl = await resolveEffectiveAcl(user); // 用户组 → 文档范围
  if (!acl.ok) throw new Forbidden("Could not resolve permissions");

  return hybridSearch(query, {
    filter: { scope: { $in: acl.scopes } },
    k: 24,
    rerank: true,
  });
}
```

这里要检查的是：检索范围是否受调用者权限约束，权限无法解析时是否拒绝访问。测试也需要包含用户无权访问的文档，确认这些内容不会进入返回结果。

### 3. 用同一组样例检查变更

修改提示词、检索器或模型后，用同一组样例比较结果，并记录运行条件。评测记录可以围绕以下问题展开：

| 检查项 | 需要保留的依据 |
| --- | --- |
| 回答是否有依据 | 回答、引用来源和人工核对结果 |
| 是否正确处理权限 | 测试身份、允许访问的范围及实际结果 |
| 响应时间 | 相同运行条件下的延迟记录 |
| 调用成本 | 模型与配置、用量和对应费用 |

记录中应同时注明测试集、运行环境和统计口径，使结果可以复核与比较。

## 协作与交付

需求和技术方案之间往往需要多轮确认。交付说明应当写清已实现的功能、尚未满足的条件，以及后续由谁维护。遇到范围或成本上的取舍，可以列出方案及影响，供业务负责人和工程团队共同判断。

## 将交付中的问题反馈给产品团队

交付中的重复问题也可以形成产品反馈。[Anthropic 的官方 FDE 岗位说明](https://job-boards.greenhouse.io/anthropic/jobs/5391016008)包含整理可复用的部署方法，并将发现反馈给产品与工程团队的职责。

记录反馈时，可以附上使用场景、复现步骤和当前处理方式。这样，团队讨论的是一个能够核对的问题，也更容易判断应当改产品、补文档，还是调整集成方式。
