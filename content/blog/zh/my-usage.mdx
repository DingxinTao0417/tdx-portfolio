> 本文记录一套用于 Claude / Codex 编程的审查流程，包含问题识别、影响分析和修复后的复查。工具参数可参照 Omnigate 的 [Claude Code 进阶](https://omnigate.cc/docs/claude-code-advanced) 文档；基础接入见[快速开始](https://omnigate.cc/docs/introduction)和[安装工具](https://omnigate.cc/docs/claude-code)。

实现、审查和业务判断需要不同的输入与检查重点。在这套流程中，Claude Opus 5 负责生成代码或方案，GPT-5.6 Sol 独立审查。问题较多或影响不清楚时，再由 Claude Opus 5 辅助解释和比较方案，由负责人决定修复范围。

下面的模型档位是使用示例，具体选择以账户可用列表为准：

| 阶段 | 角色 | 示例档位 |
| --- | --- | --- |
| 写代码 / 改方案 | Claude 执行者 | Claude Opus 5 |
| 独立审查 | Codex 审查员 | GPT-5.6 Sol |
| 业务决策辅助 | Claude 分析者 | Claude Opus 5 |

具体模型 ID 可在 [Omnigate 模型广场](https://omnigate.cc/pricing)核对。

## 第一阶段：独立代码审查（GPT-5.6 Sol）

代码或计划完成后、合并之前，先检查正确性、边界情况、安全和需求符合度。

这一阶段集中处理影响正确性的问题。重构、命名、风格和注释建议可以另行安排，让问题清单保持明确的范围。

### 审查提示词示例

```text
你是一名资深安全架构师，正在审查另一个 AI 助手编写的计划/代码。
你的任务是独立验证其正确性。

只回答下面 4 点。严禁建议重构、重命名、风格调整或添加注释。

审查清单：
1. 逻辑是否正确？（业务流程是否跑得通）
2. 是否遗漏边界情况？（空值、并发、超时、极限数据）
3. 是否存在安全隐患？（注入、越权、敏感信息泄露、资源耗尽）
4. 是否符合既定需求？（对照原始需求，有无功能偏离）

输出要求：
- 只报告「确定的」Bug、逻辑错误和安全隐患
- 不确定的标成「存疑」并说明缺什么信息，不要装作肯定
- 一轮回答内给完整清单，按严重程度排序
- 每条问题写清：位置（文件/函数/步骤）、现象、为何是错的
```

### 执行步骤

1. 将本轮改动（diff / 关键文件 / 方案段落）和原始需求一起提供给 GPT-5.6 Sol。
2. 使用上面的角色设定，再提出审查请求，例如：

```text
/goal 本轮对话的改动还有啥问题吗
```

3. 检查问题清单后，可以继续请求修复：

```text
/goal 处理掉发现的问题
```

按清单逐条修复后，再执行一轮审查。对于尚不能确认的问题，保留其缺失信息和接受该风险的决定。

### 保持审查范围清楚

重构和风格讨论可以单独处理，不相关的 PR 分开审查。每轮使用同一批改动和对应需求，方便追踪问题是否解决。

## 第二阶段：业务决策辅助（Claude Opus 5）

以下情况可以增加影响分析：

- 第一阶段发现较多问题，需要梳理优先级。
- 技术逻辑复杂，需要解释审查结论。
- 是否修复、如何修复，取决于业务影响和可接受的风险。

这一阶段说明各方案的后果和取舍，为负责人决策提供参考。

### 影响分析提示词示例

模板里的组织规模类比用于讨论可能的处理方式，不能作为某家公司实际流程的依据。使用时仍需结合当前项目的业务影响和约束。

```text
你是一名大厂技术总监，正在审阅技术方案与审查意见。

交互要求：
1. 如果我没看懂，请先用最简单的非技术语言（外行也能懂）解释核心逻辑，再展开细节。
2. 结合具体业务场景说明每个问题会造成什么实际影响
   （例如：数据对不上、接口不可用、账算错、权限被绕过、资源被打爆）。
3. 终极决策参考：若同样问题出现在一线大厂（阿里 / 腾讯 / 字节等）的生产环境，
   他们更可能怎么处理？例如：
   - 直接拒绝合并
   - 必须改方案再合
   - 先合但加监控 / 限流 / 开关
   - 紧急 Hotfix
   - 可记债务、排期再修
4. 给出不同方案的利弊对照，由我做最终裁决。不要替我选「最优雅」的那一个。
```

### 执行步骤

向 Claude Opus 5 提供：

- 相关代码或方案片段
- GPT-5.6 Sol 输出的原始问题清单
- 业务背景，包括使用者以及资金、数据、权限的敏感程度

可以继续追问：「第 3 条如果先上线会产生什么影响？」「在当前项目中，这个问题是否需要阻止合并？」

## 组合后的执行顺序

1. 用 Claude Opus 5 生成代码或方案。
2. 将同一批改动交给 GPT-5.6 Sol，使用第一阶段提示词审查。
3. 如果问题严重或影响不清楚，将问题清单和代码交给 Claude Opus 5，使用第二阶段提示词分析。
4. 由负责人确认哪些问题必须修复、哪些可以延后，以及哪些属于误报。
5. 交给 GPT-5.6 Sol 执行修复：`/goal 处理掉（你确认要修的）问题`。
6. 重复 2～5，直到已确认的必修问题处理完成。

审查深度可以根据改动风险安排：

- 小改动可以先执行第一阶段，再根据发现的问题决定是否需要第二阶段。
- 计费、鉴权、多租户和并发相关改动，适合安排完整审查，并在决定前澄清存疑项。
- 两个模型可以使用不同密钥和不同会话。实现与审查分别进行，审查时重新对照原始需求验证。
